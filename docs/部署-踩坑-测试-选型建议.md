# 本地批处理听译：部署、踩坑、测试与选型建议

更新时间：2026-06-11

本文记录当前 `FunASR` 项目内本地批处理听译工具的部署方式、已验证路线、踩坑记录、测试命令和模型选型建议。目标读者是继续开发、部署和做验收 benchmark 的同学。

## 1. 当前结论

当前阶段推荐把 `服务端 VAD + Qwen3-ASR + vLLM + 热词` 作为优先生产候选，把 `服务端 VAD + Fun-ASR-Nano + vLLM` 作为稳定基线，把 `服务端 VAD + Qwen3-ASR` 非 vLLM 作为准确率/兼容性对照路线。

VAD 是当前批处理 pipeline 的基础阶段，不是单独的模型选型路线。客户端只负责递归扫描、上传和写出结果；服务端先用 VAD 过滤无效音频并切出有效语音段，再把这些语音段送入 ASR。

已验证路线：

| 路线 | VAD | 状态 | 主要结论 |
|---|---|---:|---|
| `fun-asr-nano-vllm` | 服务端开启 | 可用 | 工程最稳，batch、`.md/.srt/.json` 全链路可用 |
| `qwen3-asr` | 服务端开启 | 可用 | 非 vLLM 路线可跑，但同批音频耗时最长 |
| `qwen3-asr-vllm` | 服务端开启 | 可用 | 当前同批音频速度最好，是后续重点路线 |
| `qwen3-asr-vllm + ForcedAligner` | 服务端开启 | 可用 | 全 pipeline 可跑通，JSON 可输出词级对齐；句级 `.md/.srt` 正常生成 |

Docker 服务化已完成基础验证。当前推荐对外集成入口是 `POST /asr/subtitles`，上传一个或多个音频文件后返回 ZIP，ZIP 内包含 `.md/.srt/.json`，单文件失败时返回对应 `.error.json`。详细交付文档见 `docs/docker部署踩坑以及使用指南.md`。

同一批 6 个课堂音频的现有 benchmark：

| 路线 | batch size | 总耗时 | 说明 |
|---|---:|---:|---|
| `fun-asr-nano-vllm` | 2 | 481.853s | 输出目录：`听译结果/` |
| `qwen3-asr` | 2 | 1778.255s | 输出目录：`听译结果_qwen3_asr/` |
| `qwen3-asr-vllm` | 2 | 296.059s | 输出目录：`听译结果_qwen3_asr_vllm/` |

`ForcedAligner` 当前只做了短样本端到端烟测，确认 pipeline 可用；还没有对 6 个完整课堂音频做全量 benchmark。建议后续单独测一次，因为强制对齐会额外消耗显存和耗时。

热词机制已完成短样本实际推理 A/B。结论是：`qwen3-asr-vllm + 热词` 对课堂专业词提升明显，warm 状态下几乎不增加推理耗时；`fun-asr-nano-vllm + 热词` 也能提升部分术语命中，但更容易出现热词诱导和重复/乱码副作用，因此 Nano 路线的热词应保守使用。

## 5. 客户端批处理命令

默认输入输出：

- 输入：`./音频文件`
- 输出：`./听译结果`
- 递归扫描输入目录
- 输出目录保持输入目录层级
- 每个音频输出 `.md`、`.srt`、`.json`

示例：

```bash
uv run batch-transcribe \
  --input-dir ./音频文件 \
  --output-dir ./听译结果_qwen3_asr_vllm \
  --server-url http://127.0.0.1:8900 \
  --route qwen3-asr-vllm \
  --batch-size 2 \
  --retries 0 \
  --overwrite \
  --language 中文
```

热词示例：

```bash
uv run batch-transcribe \
  --input-dir ./音频文件 \
  --output-dir ./听译结果_qwen3_asr_vllm_hotwords \
  --server-url http://127.0.0.1:8900 \
  --route qwen3-asr-vllm \
  --batch-size 2 \
  --retries 0 \
  --overwrite \
  --language 中文 \
  --hotword-file ./hotwords.txt
```

热词文件建议每行一个词，避免一次性塞入整本教材术语。对 `qwen3-asr-vllm` 可以放课程主题相关术语；对 `fun-asr-nano-vllm` 应更保守，只放当前音频高度相关、容易错写的少量术语。

ForcedAligner 烟测命令：

```bash
uv run batch-transcribe \
  --input-dir /tmp/funasr_m4a_voice/音频文件 \
  --output-dir /tmp/funasr_qwen_vllm_fa_smoke5/听译结果 \
  --server-url http://127.0.0.1:8905 \
  --route qwen3-asr-vllm \
  --batch-size 1 \
  --retries 0 \
  --overwrite \
  --language 中文 \
  --no-speaker-diarization
```

烟测结果：

- 成功输出：`sample_voice.md`、`sample_voice.srt`、`sample_voice.json`
- 总耗时：45.8s，其中包含 Qwen3-ASR vLLM 首次懒加载
- JSON：`segments[0].words` 含 96 个 ForcedAligner 对齐项
- `.md/.srt`：仍按句级字幕输出

## 6. VAD 在 pipeline 中的位置

当前批处理服务端的固定顺序是：

```text
原始音频 -> 服务端 VAD -> 有效语音段 -> ASR -> 可选 SPK/ForcedAligner -> .md/.srt/.json
```

关键约束：

- 客户端不做音频切分，只上传原始音频文件。
- 服务端 VAD 先过滤静音和无效音频，再按有效语音段调用 ASR。
- `fun-asr-nano-vllm` 通过 `process_audio()` 内部调用 `_vad_model.generate(...)`。
- `qwen3-asr` 和 `qwen3-asr-vllm` 通过 `prepare_qwen_segments(...)` 统一完成 VAD 切段。
- ForcedAligner 在 ASR 之后运行，只对 ASR 已产出的文本做词级对齐，不参与 VAD 决策。

因此，选型建议中的排序只比较 ASR 主模型、vLLM 形态和是否启用 ForcedAligner；VAD 默认作为服务端基础能力存在。

## 7. 踩坑记录

### 7.1 不要使用系统 Python

曾明确要求不要使用系统 Python。当前项目所有命令都应通过：

```bash
uv run ...
```

原因：

- 当前 Python 是 `3.13`
- `torch/vllm/qwen-asr` 组合依赖敏感
- 系统 Python 会破坏隔离，导致 CUDA、vLLM、transformers 版本不可控

### 7.2 Qwen3-ASR vLLM 输入不能传裸 numpy array

`qwen-asr` 的 `Qwen3ASRModel.LLM.transcribe()` 对 audio 输入格式有要求。服务端适配时要传：

```python
audio=[(seg_audio, sr) for seg_audio in seg_audios]
```

不要传裸 `np.ndarray` 列表，否则会触发输入校验错误。

### 7.3 ForcedAligner 返回结构不是 dict/list

`qwen-asr==0.0.6` 的 ForcedAligner 返回：

- `ASRTranscription.time_stamps`
- 类型类似 `ForcedAlignResult`
- 内部 item 是 dataclass，字段为 `text/start_time/end_time`

之前只按 dict/list 解析，导致 JSON 没有 `words`。现在已增加统一解析函数，支持：

- dict
- tuple/list
- dataclass/object with `start_time/end_time`

### 7.4 同一服务加载多个 vLLM engine 会显存冲突

`serve_vllm.py` 当前会先加载 Nano vLLM engine。第一次请求 `qwen3-asr-vllm` 时再加载 Qwen3-ASR vLLM engine。

如果使用同一个 `--gpu-memory-utilization`：

- 过高：Qwen 加载时剩余显存不足
- 过低：Qwen 没有足够 KV cache

已新增参数：

```bash
--qwen-gpu-memory-utilization
--qwen-max-model-len
```

ForcedAligner 烟测通过配置：

```bash
--gpu-memory-utilization 0.10
--qwen-gpu-memory-utilization 0.20
--qwen-max-model-len 32768
```

### 7.5 Qwen3-ASR vLLM 默认 max model len 太大

`qwen-asr` 默认会让 vLLM 使用 `max_seq_len=65536`。在同一 GPU 同时保留 Nano engine、Qwen engine、ForcedAligner 时，KV cache 可能不够。

典型报错：

```text
To serve at least one request with the models's max seq len (65536), 7.0 GiB KV cache is needed...
```

处理方式：

```bash
--qwen-max-model-len 32768
```

对当前 pipeline 是合理的，因为服务端先通过 VAD 切分音频，不需要让单个 Qwen 请求承担超长上下文。

### 7.6 热词测试时也要注意 Qwen 懒加载显存

热词 A/B 测试时，临时服务先加载 Nano engine，第一次请求 `qwen3-asr-vllm` 时才懒加载 Qwen engine。若同一张 GPU 上已有其他 vLLM engine，`--qwen-gpu-memory-utilization` 过高会失败。

实际遇到的报错：

```text
Free memory on device cuda:0 (16.76/79.32 GiB) on startup is less than desired GPU memory utilization (0.25, 19.83 GiB).
Decrease GPU memory utilization or reduce GPU memory used by other processes.
```

临时测试通过配置：

```bash
--gpu-memory-utilization 0.18
--qwen-gpu-memory-utilization 0.18
--qwen-max-model-len 8192
--qwen-max-inference-batch-size 16
--qwen-max-new-tokens 1024
```

这组参数适合短样本验证，不代表生产最佳吞吐配置。生产应优先给 Qwen 主服务独占或半独占 GPU，再把 `qwen-max-model-len` 和 batch size 调回更合理的吞吐配置。

### 7.7 `hub="ms"` 与本地路径并用

模型下载和缓存使用 ModelScope，但服务启动时优先用本地路径。这样能避免每次启动重复下载，同时保留 ModelScope 目录结构。

注意：本地路径中 ModelScope 会把版本号中的点转义，例如：

```text
Qwen3-ASR-1___7B
Qwen3-ForcedAligner-0___6B
```

### 7.8 `.srt/.md` 当前是句级，不是词级

ForcedAligner 的词级对齐已经写入 JSON 的 `words` 字段；但 `.srt` 和 `.md` 当前仍以 postprocessed 句级段落输出。

这是符合当前需求的：时间戳粒度为句级，课堂听译文档需要可读段落，而不是逐字字幕。

如果后续要导出词级字幕，应新增独立开关，不建议覆盖默认句级输出。

### 7.9 Docker 内 `uv sync` 需要项目元数据

构建 Docker 镜像时，`uv sync --frozen` 会读取项目元数据。Dockerfile 不能只复制源码目录，还必须复制：

```text
README.md
LICENSE
MODEL_LICENSE
pyproject.toml
uv.lock
```

否则构建阶段会失败。

### 7.10 vLLM/Triton 运行期需要 Python 头文件

Docker 镜像内除了 Python 运行时，还需要安装开发头文件：

```text
python3.10-dev
python3.11-dev
```

实际遇到过缺少 `/usr/include/python3.10/Python.h` 导致 Triton/vLLM 运行期编译失败。

### 7.11 Docker 中本地 SPK 路径需要注册名加 `model_path`

容器内说话人模型挂载路径为：

```text
/models/iic/speech_eres2netv2_sv_zh-cn_16k-common
```

不能只把这个本地路径当作 FunASR 注册模型名。当前服务端已适配为：

```text
model = iic/speech_eres2netv2_sv_zh-cn_16k-common
model_path = /models/iic/speech_eres2netv2_sv_zh-cn_16k-common
```

接口调用方无需感知，但部署时必须保证该目录存在。

- `qwen3-asr-vllm + 热词` 是当前热词场景的首选路线。

## 9. 模型选型建议

### 9.1 推荐排序

当前建议：

1. `服务端 VAD + qwen3-asr-vllm + 热词`
2. `服务端 VAD + qwen3-asr-vllm`
3. `服务端 VAD + fun-asr-nano-vllm`
4. `服务端 VAD + qwen3-asr`
5. `服务端 VAD + qwen3-asr-vllm + ForcedAligner`

说明：

- `qwen3-asr-vllm` 在当前同批 6 个音频中速度最好，适合作为主路线继续人工抽检质量。
- `qwen3-asr-vllm + 热词` 在短样本 A/B 中显著改善课堂专业词识别，warm 推理耗时基本不变，建议作为实际课堂听译默认形态。
- `fun-asr-nano-vllm` 工程最稳，适合作为回退路线和基线；如果启用热词，需要控制热词数量，避免热词诱导和重复 token。
- `qwen3-asr` 非 vLLM 明显慢，除非遇到 vLLM 兼容问题，否则不建议生产默认使用。
- `ForcedAligner` 可用，但会增加部署和显存复杂度；若默认只输出句级 `.md/.srt`，不建议默认打开。需要词级对齐或更精确时间戳时再启用。
- VAD 是上述路线的默认服务端基础阶段，因此推荐排序比较的是 ASR 主模型、vLLM 形态和是否启用 ForcedAligner。

## 10. 生产部署建议

短期建议：

- 先用 `服务端 VAD + qwen3-asr-vllm + 热词` 做主路线。
- 服务端 batch size 先设 `2`，稳定后再压测 `4`。
- 默认关闭 ForcedAligner。
- 默认输出句级 `.md/.srt`，JSON 保留原始 segments。
- 保留 `服务端 VAD + fun-asr-nano-vllm` 服务作为回退。
- 热词文件按课程/章节维护，避免将全量术语表无差别传入每个音频。
- 对外系统集成优先使用 Docker 服务的 `POST /asr/subtitles`，不要让业务侧自行拼 `.srt/.md`。
- 接口侧保存返回 ZIP 后，应检查是否存在 `.error.json`，并记录 `processing_time`、`rtf`、`status`、`error`。
- `qwen3-asr-vllm` 是懒加载，首次请求应设置更长超时；warm 请求再进入正常 SLA 统计。

如果要启用 ForcedAligner：

- 单独部署一套服务，不要和主吞吐服务混用。
- 使用独立端口，例如 `8905`。
- 先固定 `--qwen-max-model-len 32768`。
- 对完整 6 个课堂音频重新做 benchmark。
- 监控 GPU 显存、失败率、RTF 和 JSON `words` 完整性。

推荐部署形态：

| 服务 | 路线 | 端口 | 用途 |
|---|---|---:|---|
| 主服务 | `服务端 VAD + qwen3-asr-vllm + 热词` | 8900 | 日常批处理 |
| 回退服务 | `服务端 VAD + fun-asr-nano-vllm` | 8899 | 稳定基线/故障回退，热词保守启用 |
| 对齐服务 | `服务端 VAD + qwen3-asr-vllm + ForcedAligner` | 8905 | 需要词级对齐时使用 |
