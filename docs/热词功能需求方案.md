# ASR Pipeline 热词功能需求方案

## 目标

为本地批处理听译工具的两条生产候选路线增加热词能力：

- `fun-asr-nano-vllm`
- `qwen3-asr-vllm`

热词用于提升课程、人名、术语、专有名词等领域词的识别稳定性。当前阶段只做听译，不做翻译；输出仍保持 `.md`、`.srt`、`.json`，时间戳粒度仍为句集。

## 当前项目支持情况

项目中已有可复用热词实现，不需要从零设计模型侧能力。

### Fun-ASR-Nano vLLM

`fun-asr-nano-vllm` 原生支持 `hotwords` 参数。

复用点：

- `funasr/models/fun_asr_nano/inference_vllm.py`
  - `FunASRNanoVLLM.generate(..., hotwords: List[str] = None, language: str = None, ...)`
  - 内部 `_build_prompt_text()` 会把热词拼进提示词：
    - `热词列表：[词1, 词2]`
- `funasr/models/fun_asr_nano/model.py`
  - PyTorch `AutoModel` 路线同样通过 `get_prompt()` 支持 `hotwords`。
- `examples/industrial_data_pretraining/fun_asr_nano/serve_vllm.py`
  - `/asr` 和 `/asr/batch` 已有 `hotwords: str = Form(default="")`。
  - batch 接口已将逗号分隔字符串解析为 `hw_list`，并传给 `process_audio()`。
- `examples/industrial_data_pretraining/fun_asr_nano/serve_realtime_ws.py`
  - 支持 `--hotword-file` 默认热词文件。
  - WebSocket 支持运行时 `HOTWORDS:` 指令。

结论：`fun-asr-nano-vllm` 服务端路径基本已具备能力，主要缺口在批处理客户端 CLI/config 暴露、热词文件读取、测试和文档。

### Qwen3-ASR vLLM

`qwen3-asr-vllm` 当前实现通过 `context` 参数承载热词提示。

复用点：

- `examples/industrial_data_pretraining/fun_asr_nano/serve_vllm.py`
  - `process_audio_qwen3_vllm(..., hotwords=None, ...)`
  - 当前逻辑：
    - `context = " ".join(hotwords) if hotwords else None`
    - `model.transcribe(..., context=context, ...)`
- `qwen-asr` 的 vLLM API 调用方式使用 `Qwen3ASRModel.LLM(...).transcribe(...)`，现有服务端已经接入。

结论：`qwen3-asr-vllm` 可复用现有 `context` 通道，但建议统一格式为更明确的热词提示文本，而不是简单空格拼接，以降低模型误解风险。

## 功能需求

### 输入方式

批处理客户端支持三种热词来源：

1. 命令行直接传入：
   - `--hotwords "线性映射,矩阵表示,特征值"`
2. 热词文件：
   - `--hotword-file ./hotwords.txt`
   - 每行一个热词。
   - 空行忽略。
   - 支持 `#` 开头的注释行。
3. YAML 配置：
   - `hotwords`
   - `hotword_file`

默认不自动读取 `./hotwords.txt` 或示例目录中的 `热词列表`。热词必须由命令行或 YAML 显式启用，避免误读仓库样例文件导致识别行为不透明。

优先级建议：

命令行 `--hotwords` > 命令行 `--hotword-file` > YAML `hotwords` > YAML `hotword_file`。

如果同时配置多个来源，应合并去重，并保留首次出现顺序。为了便于调试，终端进度和 JSON 元信息应显示最终热词数量。

### 热词格式

推荐统一内部结构为 `list[str]`。

支持外部输入格式：

- 逗号分隔：`线性映射,矩阵表示`
- 中文顿号分隔：`线性映射、矩阵表示`
- 换行分隔：热词文件默认格式

清洗规则：

- 去掉首尾空白。
- 忽略空词。
- 去重。
- 默认最多保留 200 个热词，避免提示词过长影响识别稳定性和吞吐。
- 单个热词默认不超过 64 个字符；超过时给出警告并跳过或截断，建议第一版选择跳过。

### 服务端接口

继续复用现有 `/asr/batch` 的 multipart form 字段：

```text
hotwords=线性映射,矩阵表示,特征值
```

不建议第一版改成 JSON 字段，因为当前客户端使用 `files + data` 的 multipart 请求，保持兼容成本最低。

响应中建议增加批次级元信息：

```json
{
  "hotwords_count": 3,
  "hotwords_applied": true
}
```

单文件结果中也可增加：

```json
{
  "hotwords_count": 3
}
```

注意：不要把完整热词表写入 `.md`、`.srt` 或默认 `.json`，避免术语表泄露和字幕污染。当前阶段只写热词启用状态和数量。

### 模型路由行为

#### fun-asr-nano-vllm

服务端调用保持：

```python
_engine.generate(inputs=seg_audios, hotwords=hw_list, language=language, ...)
```

这条路线是项目原生支持，作为热词功能的基准实现。

#### qwen3-asr-vllm

服务端调用建议从当前：

```python
context = " ".join(hotwords)
```

调整为：

```python
context = "以下是本段音频可能出现的专有名词、课程术语或人名，请在转写时优先参考：线性映射、矩阵表示、特征值"
```

原因：

- `qwen-asr` 的 vLLM 路线没有 `hotwords` 命名参数，当前可复用的是 `context`。
- 明确说明用途比裸词拼接更稳定。
- 中文课程音频中，顿号分隔比空格分隔更符合语义。

需保留一项配置：

- `hotword_prompt_template`

默认模板：

```text
以下是本段音频可能出现的专有名词、课程术语或人名，请在转写时优先参考：{hotwords}
```

### 与 VAD / ForcedAligner 的关系

热词在服务端 VAD 之后、ASR 调用时注入。完整顺序固定为：

```text
原始音频 -> 服务端 VAD -> 有效语音段 + 热词 -> ASR -> 可选 ForcedAligner -> 输出
```

组件边界：

- VAD 不读取热词，也不根据热词调整切段。
- ASR 路由消费热词：Nano 路线使用 `hotwords` 参数，Qwen3-ASR 路线使用模板化 `context`。
- ForcedAligner 不接收热词，只对 ASR 已产出的最终文本做词级对齐。
- 客户端不做音频切分，只负责解析热词、上传原始音频和写出结果。

需要注意：

- VAD 误删的音频不会进入 ASR，热词无法恢复这部分内容。
- VAD 切得过碎时，术语上下文可能被切断；热词可以缓解识别偏差，但不能替代合理切段。
- 每个 VAD 后的有效语音段都会携带同一份热词，热词过多会增加 Qwen3-ASR `context` 成本。
- 如果热词诱导 ASR 产出音频中不存在的词，ForcedAligner 可能给这些词生成不稳定的词级时间戳。

### CLI 和配置

`BatchConfig` 新增字段：

```python
hotwords: tuple[str, ...] = ()
hotword_file: Path | None = None
max_hotwords: int = 200
max_hotword_chars: int = 64
hotword_prompt_template: str | None = None
```

CLI 新增参数：

```text
--hotwords
--hotword-file
--max-hotwords
--max-hotword-chars
```

客户端 `BatchTranscriptionClient.transcribe_batch()` 新增 `hotwords` 参数，并把热词序列化为逗号分隔字符串提交给 `/asr/batch`。

### 输出

`.srt`：

- 不展示热词。
- 保持字幕格式纯净。

`.md`：

- 默认不展示完整热词。
- 在文档头部只展示：`热词：已启用，N 个` 或 `热词：未启用`。

`.json`：

- 写入热词元信息：
  - `hotwords_applied`
  - `hotwords_count`
- 不写完整热词列表。

### 进度展示

终端启动时显示：

```text
Route: qwen3-asr-vllm
Hotwords: enabled, 37 terms
```

批次失败时，如果失败与热词有关，应保留服务端错误，例如：

```text
failed: hotwords payload exceeds max_hotwords=200
```

## 测试方案

按测试驱动开发推进。

### 单元测试

新增热词解析测试：

- 逗号、顿号、换行解析。
- 空行和注释过滤。
- 去重保序。
- 超长热词处理。
- `max_hotwords` 限制。

新增客户端测试：

- `BatchTranscriptionClient` 会把热词提交到 `/asr/batch`。
- 无热词时不改变现有请求。

新增服务端测试：

- `fun-asr-nano-vllm` 路由收到 `hotwords="线性映射,矩阵"` 后，`process_audio()` 得到 `["线性映射", "矩阵"]`。
- `qwen3-asr-vllm` 路由收到热词后，`process_audio_qwen3_vllm()` 得到同样列表。
- `process_audio_qwen3_vllm()` 调用 fake model 时，`context` 使用模板化文本，而不是裸空格拼接。

### 集成冒烟测试

使用短音频验证：

1. 不加热词跑一次。
2. 加热词跑一次。
3. 对比 `.json` 中文本是否更倾向保留指定术语。
4. 验证 `.md/.srt` 格式不被热词元信息污染。

### Benchmark

在现有同一批 `./音频文件` 上分别跑：

- `qwen3-asr-vllm` 无热词
- `qwen3-asr-vllm` 有热词
- `fun-asr-nano-vllm` 无热词
- `fun-asr-nano-vllm` 有热词

记录：

- 总耗时
- 单文件耗时
- RTF
- 失败原因
- 命中热词前后的关键片段差异

## 实施步骤

1. 增加 `batch_transcriber/hotwords.py`，实现热词加载、解析、去重、校验。
2. 扩展 `BatchConfig` 和 CLI 参数。
3. 扩展 `BatchTranscriptionClient.transcribe_batch()`，提交 `hotwords` 表单字段。
4. 服务端保持 `/asr/batch` 兼容；补充响应元信息。
5. 调整 `process_audio_qwen3_vllm()` 的 `context` 构造逻辑，支持模板。
6. 更新 `.md/.json` 渲染元信息。
7. 补齐单元测试。
8. 用短音频做冒烟测试。
9. 用实际 `./音频文件` 做 benchmark。

## 风险和约束

- 热词不是强制替换，只是模型提示或上下文 bias，不能保证 100% 命中。
- 热词过多会拉长 prompt，可能降低吞吐或引入幻觉。
- `qwen3-asr-vllm` 使用 `context`，效果依赖 `qwen-asr` 对上下文的遵循程度，需要用真实音频验证。
- 如果热词包含错误词，可能导致误识别被放大。
- 说话人分离、VAD 切段后，每个 VAD 片段都会带同一份热词；超大热词表会重复增加推理成本。
- 热词不会改变 VAD 和 ForcedAligner 的接口；第一版只影响 ASR 输入提示。

## 待确认问题

1. 是否需要为不同子目录配置不同热词表，例如每门课一个术语表？第一版建议不支持，只维护一个显式传入的热词文档。
2. 热词数量上限第一版是否接受默认 200？
3. 是否需要支持热词权重，例如 `线性映射 20`？当前 Nano/Qwen prompt 路线没有真正权重语义，第一版建议不支持。
